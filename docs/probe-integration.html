1. 做了什麼

  • 發送端狀態機：手機一次只送一個階段指令，等該階段的終止回應（OK / ERROR / TIMEOUT）才送下一個；BUSY 自動 RESET 後重送一次、逾時自動 RESET，確保 Probe 永遠回到 IDLE。
  • /probe 頁面：只搜尋名稱以 MotoBattery_Probe 開頭的 BLE 裝置；連線後可逐一執行 4 個階段、看即時電壓與夾子狀態（STATUS）、重置裝置、檢視藍牙收發紀錄；保留「模擬 Probe」供無硬體時測試。
  • 驗車整合：買家或賣家在 Probe 已連線時進入驗車，會跳出「要使用 Probe 量測電瓶嗎？」。選「是」→ 量測與聲音、震動同步嵌入冷車／熱車錄製；選「否」→ 流程完全照舊。
  • 判定：App 依原始數值用「放寬版」門檻重新判定，不受韌體版本影響；韌體自己的判定保留在原始紀錄。
  • 報告：量測結果存成驗車證據，並在報告底部新增「Probe 電瓶檢測」區塊。

3. 指令與 JSON 格式

手機寫入純文字指令；Probe 以 JSON notify 回覆。以下為實機實際收到的格式（夾子未接電瓶時）與文件定義的成功格式。

指令階段引擎韌體行為App 逾時
OCV / 1靜態電壓熄火100ms 穩定後 64 次超取樣5 s
IR / 2負載內阻熄火單次 ~30ms MOSFET 脈衝5 s
CRANK / 3發動壓降發動中先回 WAITING_TRIGGER，10 s 內等 <11.5V，觸發後擷取 1 s16 s
CHARGE / 4回充檢驗運轉中先回 STABILIZING，等 5 s 後取樣 2 s14 s
RESET / 0手動重置任何回 RESET_OK，執行中也接受—
STATUS / ?狀態查詢任何STATUS_REPORT（文件未列，實機有）2 s

4. 手機端狀態機（發送端）

所有階段指令都經過同一個佇列（ProbeClient.runStage），一次只會有一個階段在跑。

  • 封包重組：以大括號深度切出完整 JSON（忽略字串內的括號），即使一則 JSON 被拆成多個 notify 也能還原。
  • BUSY：表示韌體還在跑一個 App 已放棄的階段 → 送 RESET、等 150ms、重送一次；第二次仍 BUSY 才視為失敗。
  • RESET_OK 中途出現（使用者按重置、取消錄製）：立刻結束目前等待，不佔住佇列到逾時。
  • STATUS：不進佇列、階段執行中不輪詢；/probe 頁每 2 秒查一次（不寫入通訊紀錄，避免洗版）。

5. 判定門檻（放寬版）

依需求取韌體與手寫規劃中「較寬鬆」的一方，由 App 端重新判定。韌體回傳的 result/judgment 仍完整保存在證據的 firmware 欄位。

負載內阻 IR<25 良好；25–40 衰退；≥40 損壞（mΩ）同左< 25 良好 < 40 衰退 ≥ 40 損壞

6. 驗車流程整合

賣家與買家都適用。問句只在 Probe 已連線時出現、每筆驗車只問一次（答案記在手機），而且會等導覽與車型／年份關卡結束後才出現。

冷車＋引擎檢查（23 秒錄製）

買家熱車檢查（18 秒錄製）

熱車錄製一開始就送 CHARGE（約 7 秒，落在 0–9 秒怠速區段），作為真正的「熱車回充」量測。

例外處理

  • 選了「使用」但 Probe 沒連線 → 開始前顯示提示與「重新連線 Probe」按鈕；不連也能照常錄製（不量電瓶）。
  • 夾子沒接上電瓶（STATUS 回報）→ 開始前顯示警告。
  • 任何一段量測失敗都不會擋住驗車：Probe 是附加資料，檢查項目仍以聲音／震動為準。
  • 錄製取消或中斷 → 送 RESET，該次未完成的量測不保存。

7. 資料儲存與報告

每段結果一到就寫成一筆驗車證據（Firestore verifications/{id}/evidence），不計入必填進度與評分：

{
  itemId: "PROBE-BATTERY",          // PREP-04 手動量測則用 "PREP-04"
  type: "voltage", captureSource: "probe",
  metadata: {
    stage: "CRANK", session: "cold" | "hot" | "manual",
    status: "OK", grade: "WARNING", judgment: "觀察（低溫易熄火）",   // App 放寬版判定
    primaryValue: 8.7, values: { v_initial: 12.68, v_min: 8.7, v_drop_diff: 3.98 },
    deviceName: "MotoBattery_Probe", probeMode: "ble",
    firmware: { ...韌體原始 JSON，含其 result/judgment }
  }
}

報告（擁有者報告、分享報告）底部顯示「Probe 電瓶檢測」，每個「情境 × 階段」只列最新一筆，依 冷車 → 熱車 → 手動 排序；沒用 Probe 的驗車不會出現此區塊。

9. 實機抓到的問題（已修正）

中文判定變亂碼：第一次以網頁版連實機時，韌體回傳的「探針未夾緊或斷路」顯示成 æ¢éæªå¤¾ç·…。原因是藍牙外掛內建的 dataViewToText() 以 String.fromCharCode 逐位元組轉字（Latin-1），不是 UTF-8。
修正：改用每條連線一個 TextDecoder('utf-8')，並以 { stream: true } 解碼，就算一個中文字被拆在兩個 notify 也能正確組回；已加單元測試並重新以實機驗證通過。

10. 待完成 / 建議

  • Android App 原生藍牙實測：手機 USB 偵錯一直 offline（每個指令後就斷線），無法自動化安裝與操作。最新 APK 位於 android/app/build/outputs/apk/debug/app-debug.apk（指向 staging），請手動安裝後到「我的 › Probe 連接」測試；Android 12 以上第一次會詢問「附近裝置」權限。
  • 夾上真實電瓶再測 OCV / IR 數值，確認分壓比 DIVIDER_RATIO 校正。
  • 實車發動測 CRANK（需要真正的啟動壓降才會觸發）與 CHARGE（引擎運轉中）。
  • 建議韌體門檻改成放寬版（§5），並在 STATUS 中加入韌體版本欄位，方便 App 顯示與相容判斷。
